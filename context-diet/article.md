# 我把四份 CLAUDE.md 删掉一半，最贵的浪费不是 token

昨天晚上刷 X，看到 Anthropic 的 Thariq 发了篇长文，讲 Claude 5 这代模型的上下文工程该怎么做。我顺手把链接丢给 Claude，问了一句：对我们的提示词有优化建议吗。

它回我的第一条，是我全局 CLAUDE.md 里两条规则在打架。

第一节写着：如果存在多种解读，全部呈现出来，别自己悄悄选一个。如果有不清楚的地方，停下来，说清楚哪里困惑，然后问。

往下翻两屏，我自己写的协作偏好写着：回复默认要短，结论一句话在前，理由最多一句。我同时开着一堆 agent，没耐心读长文。大多数时候我要的是你替我把关，不是把过程摊给我看。

这两条，每一次对话都同时生效。

第一条大概是去年写的，那会儿模型经常自作主张，我被坑过几次就加了这段护栏。第二条是今年加的，因为我开始并行开五六个窗口，受不了每个都写小作文。两条各自都对，摆在一起，模型每收到一条消息都得先花力气调和它们，再猜我这次到底要哪个。

我一直以为 CLAUDE.md 写太长的代价是费 token。费 token 是小事。

## 我们是怎么把它养这么肥的

回想一下你的 CLAUDE.md 是怎么长起来的。

它大概率是一次次踩坑之后攒出来的，没有哪天你坐下来设计过它。模型改了不该改的文件，你加一条「只动必须动的」。它给你写了满屏注释，你加一条「默认不写注释」。

每一条加上去的时候都有充分理由，都是真的被坑过。删的动作从来没有发生过，因为删一条要冒险，加一条不用。于是文件只增不减。

我 2023 年开始用 Claude 写代码，2024 年下半年开始重度用 Claude Code。这两年模型能力翻了几番，我的 CLAUDE.md 只是变长。里面很多条款针对的是三个版本之前那个模型的毛病，毛病早就没了，规则还在。

Thariq 那篇文章里有个数字让我坐直了：Anthropic 给 Claude Opus 5 和 Fable 5 用的 Claude Code 系统提示词，**删掉了 80% 以上，编码评测没有可测量的损失**。

原文值得读，地址在这儿：https://x.com/trq212/article/2080710971228918066

他们自己的系统提示词，比我们任何人的 CLAUDE.md 都更谨慎、更被反复验证过，删了八成还没事。那我的呢。

## 五条已经过时的老规矩

文章里最有价值的是一张对照表，讲哪些做法过时了。

**给规则，改成给判断力。** 以前要写死「绝不写注释」，因为老模型的注释确实经常是废话。现在 Claude Code 的系统提示词改成了一句话：写得跟周围代码一样，注释密度、命名、惯用法都对齐。

**给例子，改成设计接口。** 这条最反直觉。以前教模型用工具的头号办法是给示例，现在发现示例反而把它锁死在你演示过的那个解空间里。与其举例子，不如把参数名和枚举值设计好，那本身就是提示。

**全写在前面，改成渐进式披露。** 拆成树状文件，用到的时候才加载。

剩下两条比较短：同一件事不用在几个地方重复说了（老模型对上下文末尾的指令更敏感，所以要重复），该说的写进工具描述里；往 CLAUDE.md 里手动存记忆也不用了，模型自己会存。

看完这五条，我关掉推特，打开自己的四份 CLAUDE.md 开始动手。

## 四份文件，一轮改完

我改了全局那份，加上三个项目：一个刚起步的产品仓库，一个用了半年的项目管理知识库，还有一个开发了几个月的产品。

| 文件 | 前 | 后 | 变化 |
|---|---:|---:|---|
| 全局 CLAUDE.md | 6,465 | 3,762 | 少 42% |
| 产品仓库 A | 6,431 + 12,319 | 5,792 | 每会话少 69% |
| 项目管理知识库 | 19,836 | 9,338 | 少 53% |
| 产品仓库 B | 33,094 | 23,857 | 少 28% |

**内容零丢失。** 这四个字我要强调一下。删掉的全是模型自己会的、看仓库能推导出来的、或者本来就该只有一处的副本。

全局那份，我删掉了整整四节：Think Before Coding、Simplicity First、Surgical Changes、Goal-Driven Execution。条目像「不要过度抽象」「只改必须改的」「先写测试再修 bug」。

每一条都是好建议。问题是 Claude 5 已经内置了，我等于把它的系统提示词又背了一遍给它听。

该问的问题是「模型本来会不会」。「这条建议好不好」问了没用，答案永远是有用。

产品仓库 A 的问题在第一行。那行写的是 `@.claude/keel/METHODOLOGY.md`，12KB 的工程方法论，每个会话无条件全量加载。而那个项目还在验证阶段，一行业务代码没写，大部分会话在做品牌和市场调研，一个 Issue 都不碰。

`@` 做的事情，跟渐进式披露正好相反。改成按需加载的 skill 之后，每会话省掉七成，原来那个 12KB 文件我一个字没动。

项目管理知识库那份，我删掉了 41 行「Claude 什么时候该主动建任务卡」的规则。核心是一套信号计数：明确目标、多步动作、跨会话可能、有产出物，四个信号里满足三个就自动建，正好两个问一句，一个以下不建。

这是把模型本来做得不错的判断，换成它必须执行的算术，而且这算术还不更准。「正好两个信号」对一件明显值得记的事意味着什么？

压成一段判据描述之后，该守的政策一条没少：项目永不自动建、凡落盘必当场亮去向、必须走脚本分配全局编号。去掉的只是「怎么决定」的机械过程。

## 最难的那份，文件自己写着「别删」

产品仓库 B 那份 33KB，是最有意思的一个。

它开头写着一句：以下全是事故换来的，别删。

这话是对的。里面绝大部分确实是真 gotcha，每一条背后都有一次真实的返工。文章说 CLAUDE.md 应该把 token 全花在 gotcha 上，那这份文件已经是标准答案了，还怎么瘦。

翻到第三条的时候我发现，里面几乎每条规则都长成同一个形状：

```
## 铁律：X（防「Y」）
教训（2026-07-10，严重）：……三百字事故经过……根因 = ……
规则：1. …… 2. …… 3. ……
```

事故经过占了差不多一半篇幅。而它只在一种情况下才需要被读到：有人想推翻这条规则的时候。

日常施工，你读完那三百字，动作跟没读一模一样。

这就是渐进式披露的定义。

于是我建了 `docs/why-these-rules.md`，把所有事故叙事整段搬过去，一字未删，正文只留可执行的规则。文件顶部本来就有一张「什么问题去哪找真相」的表，加一行指向新文件。

搬走的九千多字里，有这么几件事：一次差点重复造轮子的事故；只增不改的决策流水导致模型按被推翻的旧决策回答；一次构建事故，本机同时存在四棵源码树、九份同名的 App 包，「改了没效果」被误判成缓存问题排查了好几天；还有一组数据，证明软性提示完全无效，模板里写着「请填写以下七段」，实测填充率 8%。

砍下来 28%，一个字的信息都没丢。

## 有一句话我特意留在了正文

按规矩，事故经过该走，规则该留。但构建那节有个例外：那次事故里最值钱的东西是一个否定式的结论，这不是缓存问题。

当时所有人的第一反应都是清缓存，包括我。清了好几轮没用，最后才发现是在错误的源码树上点了构建。如果只留「构建前确认在构建哪棵树」这条规则，下一个人遇到「改了没效果」，还是会先去清缓存，再重新推导一遍，再烧掉同样几天。

所以正文里我留了这么一句：

> 构建前先确认在构建哪棵树。本机同时有多棵源码树，每棵都有一份长得一模一样的项目文件。这不是缓存问题，别去清缓存（事故实况见 docs/why-these-rules.md）。

结论在正文，证据在档案。

判断标准是这个：知道这段，会改变我现在的动作吗？不会、但会改变我要不要跟这条规则争，那它就该进档案。

## 你可以今天就做的事

先找冲突，别急着数字数。打开你的 CLAUDE.md，看有没有两条规则在拉扯。最常见的一对是「详细说明你的推理」和「回复简短一点」。冗余只浪费 token，冲突浪费的是推理，还让行为变得不可预测。

然后对每一条问一句：模型本来会不会。会，就删。

最后一条是我这轮最大的收获：gotcha 一律搬家，不许扔。踩坑换来的东西一个字都不能少，但「规则」和「事故经过」可以分开住。分开之后文件反而更好用了，因为每一行都在告诉你该干什么，没有一行在讲故事。

Claude Code 现在内置了 `/doctor`，能自动帮你 rightsize skill 和 CLAUDE.md，也跑一下。它替你做不了的是最后那个判断：这条是真 gotcha，那它不该进垃圾桶，该去哪。

我把整套方法和这四个案例开源了，MIT 协议，一条软链就能装成 skill。项目名和业务细节做了脱敏，手法和数字都是真的。

GitHub：https://github.com/andyleimc-source/context-diet

## 最后

我们过去两年给 AI 写的所有规矩，本质上都是在补它的短板。模型的短板每三个月变一次，我们的规矩从来不变。

结果就是，你以为自己在给它装护栏，其实是在给一个已经会走路的人绑沙袋。

删完那 42% 之后，省钱是次要的，主要是它变听话了。因为终于没有两个声音同时在它耳朵边上说话。

> 要删的是噪音，不是知识。而最吵的那点噪音，往往是你自己两年前写下的那条好建议。
